    The workflow

    Eight steps to live

    Read the whole thing once before you start typing. Anywhere you see your-name, swap in your own — lowercase, hyphens instead of spaces.

    01

    Get the repo onto your machine

    Cloning downloads the whole project plus its entire history. You only ever do this once per machine.

    Terminal 
    # replace this URL with our actual repo URL
git clone https://github.com/YOUR-ORG/ai-studio-lab.git
cd ai-studio-lab
    02

    Start a branch

    A branch is your own copy of the project where nothing you do can break anyone else's work. Always branch from an up-to-date main.

    Terminal 
    git switch main
git pull
git switch -c lab/your-name
    Convention Branch names start with lab/ so anyone scanning the branch list can see at a glance what kind of change is coming.
    03

    Claim your folder

    Copy the template into a folder named after you. From here on, everything you build lives inside that folder and nowhere else.

    Terminal 
    cp -r labs/_template labs/your-name
    Why One folder per person is what makes merge conflicts almost impossible here. Two people can never collide if they never edit the same file — so stay inside your folder.
    04

    Open it in a browser

    Serve the folder locally so links and paths behave the way they will once deployed. Leave this running in its own terminal tab while you work.

    Terminal 
    python3 -m http.server 8000
# then visit http://localhost:8000 in your browser
# stop the server later with Ctrl+C
    05

    Make it yours

    Edit labs/your-name/index.html and build whatever you want. Bring your own CSS, images, and scripts — keep them in your folder. This is the part where nobody has notes for you.

    Off limits Don't edit assets/site.css, index.html, or anyone else's lab. If you genuinely need a change to a shared file, make it a separate pull request and say why — mixing it into your lab PR makes the whole thing slow to review.
    06

    Register your lab

    This is the only shared file you touch. Add one entry to the end of the array in labs/labs.js and your lab appears in the top menu and on the home page at the same time.

    labs/labs.js — diff 
    // append after the last entry, minding the comma
+  ,{
+    slug: "your-name",
+    name: "Your Name's Lab",
+    owner: "Your Name",
+    blurb: "One sentence about what you're exploring.",
+    branch: "magenta",
+    added: "2026-09-01"
+  }
    Careful Add your lines and change nothing else. Don't let your editor reformat the file on save — a tidy-up turns a 7-line diff into a 40-line one and buries the actual change.
    07

    Commit in small pieces

    Read your own changes before you commit them. Two or three focused commits beat one enormous one, because a reviewer can follow your thinking instead of reverse-engineering it.

    Terminal 
    git status                          # what changed?
git diff                            # read it before you send it

git add labs/your-name
git commit -m "Add lab page for Your Name"

git add labs/labs.js
git commit -m "Register your-name in lab index"
    Habit Write the message for the person reading the history in six months. "Add lab page for Ana" is useful. "updates" is not.
    08

    Push and open the pull request

    Pushing uploads your branch. A pull request asks the team to review it and pull it into main. Once it's approved and merged, the site rebuilds and your lab is live.

    Terminal 
    git push -u origin lab/your-name
# the terminal prints a link — open it to create the PR

    In the description, write what you built, what you'd like feedback on, and drop in a screenshot. Then review your own diff in the Files changed tab before you request anyone else. You will catch something. Everyone does.

    Merge

    What reviewers check

    Not whether your design is good — that's a critique, and we do those separately. A review asks whether this change is safe and easy to accept. Run this list over your own PR first.

    • Everything is inside your folder, apart from one entry in labs/labs.js.
    • No unrelated changes. No reformatted files, no dependency bumps, no drive-by fixes.
    • Commit messages describe the change rather than the fact that a change happened.
    • It works from a fresh clone — no broken image paths pointing at your desktop.
    • The PR description says what you built and includes a screenshot.
    • You can explain every line. If you can't, take it out. This is the one that matters.
    Note Comments on your PR are about the change, not about you. Expect a couple of rounds — that's the system working, not a rejection. "Good catch, fixed" is a complete and professional reply.
